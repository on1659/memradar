# 페르소나 진단 — 쉬운 질문지 + 직업 선택 (follow-up 사양)

> 작업 지시서. 기존 [`persona-quiz-spec.md`](persona-quiz-spec.md)로 만든 진단 탭의 **질문지 개선** 후속 작업.

## 배경 / 문제

현재 진단 문장이 개발 전문용어라 일반인이 이해하기 어렵다.

- 예) "SQL·jq·grep을 자주 쓴다", "리팩터링으로 코드를 다듬는다" — 비개발자는 무슨 말인지 모름.
- 진단 시작 화면에 맥락(나는 어떤 일을 하는 사람인지)이 없어 문장이 더 막연하게 느껴진다.

## 목표

진단 질문지를 **두 축**으로 쉽게 만든다.

1. **쉬운 표현 재작성** — 9카테고리 × 5진술 전부 일반인이 아는 말로 다시 쓴다.
2. **직업 선택** — 진단 시작 전 "당신의 직업은?"(사용자 본인 직군)을 고르게 하고, 그 직군 눈높이에 맞춘 문장을 보여준다.

## ⚠️ 핵심 긴장 — 쉬움 ↔ 변별력 (lesson L-1)

`.claude/knowledge/lessons/personality-eval.md` **L-1(바넘 효과)**: 문장이 너무 일반적이면 누구나 "맞다"고 느껴 진단이 의미를 잃는다.

- **"쉽게"가 "막연하게"가 되면 안 된다.** 각 진술은 일반인이 이해하면서도 **구체적·관찰가능한 행동**을 가리켜야 한다 (어느 쪽이 나인지 변별 가능).
- 나쁜 예(바넘): "나는 꼼꼼하게 일한다" → 누구나 yes.
- 좋은 예(구체+쉬움): "에러가 나면 원인을 끝까지 파고드는 편이다" vs "일단 되게 만든 뒤 나중에 다듬는다".
- 재작성 후 **L-2 sharpness가 떨어지지 않았는지** 본인+소수 표본으로 재변별 확인.

## 1. 쉬운 표현 재작성

### 대상
- `scripts/eval-sharpness-statements.json` (원본) + `src/data/personaStatements.ts` (앱 번들 복제본). **둘은 verbatim 동기화**(테스트가 강제) — 한쪽만 고치면 안 됨.

### 규칙
- 전문용어 제거: SQL/jq/grep/리팩터링/CI/배포파이프라인 등 → 일상어 또는 "쉬운 말(괄호 안 원어)".
- 9카테고리 구조·개수(각 5진술) **유지**. 텍스트만 교체.
- 각 진술은 한 문장, 구체적 행동 묘사, 변별 가능. 추상 형용사("성실한", "창의적인") 금지.
- 한국어/영어 양쪽 유지 (현재 구조 따름).

### 카테고리별 재작성 톤 (참고 — 정확한 문구는 Coder가 작성)
| 카테고리(AI 역할) | 쉬운 표현 방향 |
|---|---|
| feature(기능 제조) | "새 기능·화면을 만들어 달라고 자주 시킨다" |
| debug(버그 헌터) | "문제 원인을 찾는 데 시간 가는 줄 모른다" |
| refactor(정리) | "이미 되는 걸 더 깔끔하게 다듬는 편이다" |
| review(검토) | "남이 만든 걸 살펴보고 고칠 점을 짚는다" |
| writing(글쓰기) | "문서·설명·메시지 쓰는 걸 자주 맡긴다" |
| design(디자인) | "보기 좋고 쓰기 편한 화면을 신경 쓴다" |
| devops(운영) | "올리고·배포하고·자동화하는 일을 한다" |
| data(데이터) | "숫자·데이터를 뽑아보고 정리한다" |
| test(테스트) | "제대로 동작하는지 확인·점검을 챙긴다" |

## 2. 직업 선택 (사용자 본인 직군)

### UX
- 진단 시작 화면(intro)에 직업 선택 추가: **"당신의 직업은?"**
- 후보(제안 — Scout/디자인 후 확정): **개발자 / 기획·PM / 디자이너 / 데이터·분석 / 기타(일반)**.
- 고른 직군에 맞는 **눈높이 문장**으로 9쌍을 보여준다 (예: 개발자는 "코드 리뷰", 기획자는 "기획서 검토" 같은 식의 같은 의미·다른 어휘).
- "기타(일반)" = 직군 무관 기본 문장(§1에서 만든 일반판).

### 진술 사전 구조 (제안 — Scout 정찰 후 확정)
- 진술을 **직군 렌즈(lens)** 로 확장: `직군 → 카테고리 → 진술[]`. 기본(general)은 필수, 직군별은 있으면 사용·없으면 general 폴백.
- ⚠️ 이 구조 변경은 `scripts/eval-sharpness.mts`(CLI 검사 도구)와 `tests/eval-sharpness.test.mts`, 동기화 가드 테스트에 영향. **Scout가 영향 범위를 먼저 매핑하고, json 스키마 변경 시 CLI·테스트 동반 수정 또는 하위호환 유지**.

### 불변 — 측정 무결성
- 직업 선택은 **사용자 도메인 어휘**만 바꾼다. 측정 대상인 **9카테고리 자체는 그대로** (usageProfile.ts 무변경).
- 직업 선택·진술 어디에도 **측정 중인 카테고리 id/라벨 노출 금지** (바넘 무결성).
- 직군은 문장 어휘만 바꿀 뿐, **보정 계산(computeCalibration/applyCalibration…)은 동일** — 결과는 항상 9카테고리로 매핑.

## 하네스 — COMPLEX

새 분석/입력 모델(직업 선택), 진술 사전 구조 변경(파서·CLI·테스트 영향), 저장 스키마 bump → **COMPLEX**.
1. **Scout** — 진술 사전 구조(json↔ts↔eval-sharpness.mts) 의존성, 직군 렌즈 도입 시 영향 범위, 저장 스키마 v1→v2 마이그레이션 지점, intro 화면 구조 정찰.
2. 정찰 결과가 이 사양과 다르면 **멈추고 보고** (특히 json 스키마 변경의 CLI 파급).
3. **Coder** — 진술 재작성 + 직군 렌즈 + intro 직업 선택 + 저장 v2.
4. **Reviewer** — 타입·불변조건·바넘 무결성·동기화·하위호환.
5. **QA** — 흐름(직업 선택→9쌍→결과), 재검사, v1 로드, 외부호출 0, 변별력 회귀.
